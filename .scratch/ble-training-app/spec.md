# BLE Training App and IoT Device

## Problem Statement

Training results are generated by a physical BLE-enabled training device, but the operator currently lacks a reliable mobile workflow for connecting to the device, starting a session, observing progress, receiving the authoritative result, and reviewing saved sessions.

The mobile application must not become the source of truth for sensor events or elapsed time. The microcontroller owns sensor qualification, counting, timing, feedback, completion, and short-term result retention. The mobile application owns the operator workflow, BLE lifecycle, training metadata, recovery orchestration, and local persistence.

The system must remain useful without internet access. A temporary BLE disconnect must not be treated as loss of the training session: the device continues independently, and the application recovers by reconnecting and synchronizing device state.

## Solution

Build an offline-first Expo React Native mobile application connected to a BLE training microcontroller through a versioned protocol.

The application provides Dashboard, Home, History, and Settings navigation. The operator can enter optional notes, connect to one training device, start a six-ball session only after the device reaches a fully synchronized Ready state, observe device-reported progress, receive the final result, and save or discard it.

The microcontroller exposes a custom BLE service and remains authoritative for the session counter and monotonic duration. It accepts idempotent control commands, emits acknowledgements and state/progress/completion notifications, and retains the latest completed result long enough for reconnect recovery.

The application wraps the selected native BLE library behind a BLE adapter and keeps protocol encoding/decoding independent from screens. A training-session orchestration boundary consumes transport and persistence ports, drives the session state machine, deduplicates events, handles reconnect and SYNC recovery, and exposes UI-ready state. Local SQLite persistence stores saved results with a uniqueness constraint on device identity and BLE session ID.

The MVP target count is fixed at six valid ball detections. The protocol includes `targetCount` so a later product decision can make it configurable without changing the message envelope.

## Implementation Decisions

- The mobile application uses Expo React Native with TypeScript, Expo Router for navigation, Zustand for lightweight connection and training state, expo-sqlite for local persistence, and a custom development build. Expo Go is not a supported runtime because BLE requires native code.
- The initial BLE adapter candidate is `react-native-ble-manager`, wrapped behind an internal transport-neutral BLE adapter. `react-native-ble-plx` remains an allowed replacement if the technical spike shows better compatibility. Screens and training logic must not depend directly on either native library.
- The primary application seam is a training-session orchestration boundary. It accepts operator intent and device events, commands the BLE adapter, persists completed results through a repository port, and exposes observable session state. The boundary owns the Ready, Starting, Active, Recovering, Completed, Cancelled, and Error transitions.
- The orchestration boundary receives a fake BLE transport and fake persistence implementation in unit tests. This is the highest useful seam because it verifies the product behavior without coupling tests to React rendering, native BLE callbacks, or SQLite implementation details.
- Mobile ownership includes navigation, permission flow, scanning, connection lifecycle, GATT discovery, notification subscription, reconnect policy, training metadata, session orchestration, persistence, and user-facing errors.
- Microcontroller ownership includes IR validation, authoritative counting, authoritative monotonic timing, buzzer and LED feedback, deterministic completion, command validation, and retained last-result state.
- The shared protocol ownership includes custom UUID constants, protocol version, command and event codes, payload layouts, device state codes, error codes, and completion reason codes. The finalized shared constants must be checked into both mobile and firmware delivery outputs or generated from one shared specification.
- The BLE lifecycle is Disconnected → Scanning → Connecting → Discovering → Ready. Ready requires successful service discovery, required characteristic discovery, event/state notification subscription, and initial state synchronization. A transport-level Connected state alone is insufficient.
- Only one peripheral connection is active at a time. Selecting another peripheral disconnects the existing device before the new connection proceeds.
- Bluetooth permissions are requested only when the user enters a BLE-related flow, subject to the selected native library's platform requirements. Adapter-off and permission-denied states are explicit and recoverable.
- Scanning is bounded and stops after a successful connection or timeout. Service UUID filtering is preferred; service or manufacturer data filtering is the fallback when firmware advertising does not support direct service filtering.
- The logical GATT service contains four characteristics: CONTROL for app-to-device write-with-response commands; EVENT for device-to-app notifications; STATE for device state read and notification; and DEVICE_INFO for protocol, firmware, model, or serial data.
- CONTROL commands are START, STOP when firmware supports it, SYNC, and ACK_RESULT. EVENT messages are ACK, PROGRESS, COMPLETE, ERROR, and STATE_CHANGED. STATE provides a snapshot for initial and reconnect synchronization.
- Protocol version 1 uses a compact envelope with one-byte version, one-byte message type, four-byte unsigned session ID, two-byte per-session sequence, and a variable payload. Multi-byte fields are little-endian. Application-level CRC is not required for MVP because BLE provides link-layer integrity.
- START carries a one-byte target count, fixed to six for the MVP. STOP carries a reason when supported. SYNC has no payload. ACK_RESULT carries the sequence of the handled result. ACK carries command and status. PROGRESS carries count and authoritative elapsed milliseconds. COMPLETE carries count, authoritative duration milliseconds, and completion reason. STATE carries state, count, and elapsed milliseconds. ERROR carries a device error code.
- Device state codes are READY, ACTIVE, COMPLETED, and ERROR. START is accepted only in READY. A duplicate START with the same active session ID is acknowledged idempotently and must not reset state. A different START while ACTIVE is rejected.
- The application sends START using write-with-response and waits for an application ACK. The write result only confirms transport acceptance; application ACK determines whether firmware accepted the command.
- START application acknowledgement timeout is three seconds. Before retrying, the application reads or synchronizes current STATE and compares device state and session ID. The UI allows at most one retry and never blindly retransmits a command that could reset an active device session.
- The app generates the BLE session ID before START and keeps it unchanged for the entire logical session. The local database also stores a UUID string as the local primary key.
- Incoming session events are accepted only for the current session, except for an explicitly identified retained last-result recovery response. The orchestration boundary tracks the highest valid sequence for the active session and ignores older duplicates. Six-ball MVP sessions are unlikely to wrap a 16-bit sequence, but unsigned comparison behavior should remain defined for future protocol use.
- On disconnect during ACTIVE or during an unresolved START, the application enters Recovering. Reconnect attempts use bounded backoff. A successful reconnect repeats GATT discovery and notification subscription, then issues SYNC. Recovery resumes Active or produces a recovered Result based on device state and session identity.
- The device retains the latest completed result until the application acknowledges it or a newer session replaces it. The application sends ACK_RESULT only after the result has been handled according to the product flow.
- The local TrainingSession record contains a UUID primary key, BLE session ID, optional notes, target count, final count, authoritative duration, app-observed start and completion timestamps, stable device key, result status, and protocol version.
- Saved result uniqueness is enforced by the pair of stable device key and BLE session ID. Repeated COMPLETE, SYNC, or Save operations upsert the same logical result instead of inserting duplicate History rows.
- Only saved results appear in default History. Supported statuses are completed, cancelled when STOP is implemented, and recovered. The MVP retains actual final count for cancelled or error outcomes only if the selected firmware and product workflow support those outcomes.
- The application records the start timestamp when START ACK is received and the completion timestamp when COMPLETE is received or recovered. These app timestamps are display metadata; authoritative duration remains the device-provided duration.
- The mobile timer may interpolate between device updates for visual smoothness, but every PROGRESS, STATE, or COMPLETE event replaces the displayed value. The stored final duration is never calculated from the phone clock.
- The UI disables duplicate start actions after command acceptance, ignores stale events, preserves diagnostics for device errors, and does not fabricate results when the device reports ERROR or sends invalid data.
- Optional STOP remains a P1 capability. If implemented, the firmware must produce a completed or cancelled reason code and the UI must clearly distinguish a stopped partial result from a target-reached result.
- Device identity is not trusted from the advertised name alone. Discovery uses the product service and manufacturer or service data, and the application stores a stable device key where the operating system or device-provisioned identifier provides one.
- Pairing or bonding is not required for MVP unless the product threat model requires it. Production protocol handling still rejects malformed versions, unknown message types, invalid payload lengths, impossible state transitions, and unsafe session changes.
- Training notes and results remain on the device in MVP. No cloud account, authentication, remote synchronization, coach portal, or web dashboard is introduced.
- The mobile implementation is foreground-first. The microcontroller continues independently if the app is backgrounded or terminated, and the next launch can recover through best-effort reconnect and SYNC. Full background training execution is outside the MVP contract.
- The delivery sequence is a physical BLE spike, firmware protocol implementation, mobile core workflow, persistence and recovery, then QA hardening. The spike must validate the selected BLE library, custom development build, target hardware connectivity, read/write/notify behavior, and finalized UUIDs before broad feature implementation.

## Testing Decisions

- Tests verify externally observable behavior at the training-session orchestration boundary, not React component structure, native library internals, callback wiring, or SQL statement details.
- The main test fixture uses a fake BLE adapter and fake repository. It drives user commands and device events, then asserts emitted device commands, visible state, persisted outcomes, deduplication, and recovery behavior.
- The main behavior suite covers Ready → Starting → Active → Completed, rejected START, duplicate START, START timeout with state check, Active → Recovering → Active, Active → Recovering → Completed, stale session events, out-of-order and duplicate sequences, duplicate COMPLETE, idempotent Save, Discard without persistence, and device ERROR.
- Tests prove that the app cannot enter Active before an accepted application ACK and cannot start while the device is not Ready.
- Tests prove that final count and duration displayed and persisted are taken from device COMPLETE or synchronized STATE data rather than a phone-side timer.
- Tests prove that disconnect does not create a second logical session and that reconnect sends SYNC rather than a blind START.
- Tests prove that retained completed results can be restored after reconnect or app-launch recovery and that ACK_RESULT is emitted only after handling the result.
- Protocol codec tests cover valid encode/decode fixtures for every v1 command and event, little-endian integer handling, sequence and session fields, and rejection of malformed versions, unknown types, invalid lengths, truncated payloads, and impossible values.
- Persistence contract tests cover the TrainingSession shape, newest-first history ordering, local restart durability through the repository boundary, and uniqueness/upsert behavior for repeated device key and BLE session ID pairs.
- BLE adapter integration tests cover permission branches, adapter-off behavior, bounded scanning, device filtering, connection replacement, discovery failure, notification subscription, command timeout, and disconnect handling using the selected native implementation.
- Firmware tests cover IR debounce and qualification, exactly six valid detections producing one completion, duplicate START not resetting an active session, disconnect not terminating device work, retained result recovery, malformed command handling, protocol version mismatch, and invalid state transitions.
- End-to-end validation uses a custom development build and physical hardware. The minimum device matrix includes one recent Pixel-class Android device, one Samsung-class Android device, one current iPhone, and the real target microcontroller.
- Acceptance testing covers connect-to-Ready, notes and six-ball start, one START producing one device session, one feedback cycle per valid ball, COMPLETE with count six and positive duration, matching mobile result, save across app restart, discard without History, disconnect after the third ball with recovery, duplicate COMPLETE without duplicate History, and recoverable permission/adapter/scan/GATT error states.
- No test prior art exists in the current repository because it contains the product requirements document but no implementation or test suite. New tests should therefore establish the orchestration seam and fixture conventions once, then reuse them for each behavior slice.

## Out of Scope

- Cloud accounts, authentication, remote result synchronization, coach portals, web dashboards, leaderboards, and cross-device reporting.
- Simultaneous multi-device sessions or more than one active peripheral connection.
- Firmware over-the-air updates initiated by the mobile application.
- Phone-owned sensor counting or phone-owned authoritative timing.
- Classic Bluetooth; only Bluetooth Low Energy is supported.
- Background training execution managed by the phone. The device may continue independently, but full background BLE UX is not an MVP requirement.
- Configurable target counts, training templates, and configurable training programs. The protocol remains extensible, but the MVP target is six.
- Mandatory STOP support. STOP is permitted only when firmware supports a clear cancellation or completion reason and remains P1 unless product needs elevate it.
- Production-grade pairing, bonding, or application-layer authentication before a threat-model decision is made.
- Final microcontroller platform selection, electrical sensor qualification values, and hardware-specific implementation details beyond the protocol and behavioral contract.
- Replacing the selected BLE library based only on preference without first validating compatibility through the physical technical spike.
- Continuous scanning, unrestricted retry loops, or automatic creation of a new session after an ambiguous start or reconnect.

## Further Notes

- The product source flow is a Home → Start Training → Result → Save journey with Dashboard, History, Settings, and Bluetooth connection support. The explicit Ready gate is intentional: Connected is not equivalent to GATT-ready and synchronized.
- The physical device is the source of truth for count, duration, detection qualification, completion, and immediate feedback. The phone is an operator interface, recovery coordinator, and local result store.
- The protocol envelope is designed for conservative BLE MTU sizes and carries session and sequence identity so retransmission, reconnect, and duplicate notification handling are deterministic.
- The application should preserve user-facing diagnostics without logging sensitive training notes in production diagnostics.
- Responsiveness target: under normal foreground conditions, the UI should reflect a delivered PROGRESS notification within 250 ms of delivery to JavaScript.
- Battery target: scanning stops immediately after successful connection or timeout; continuous scanning is prohibited.
- The technical spike must finalize generated 128-bit UUID values, validate the native BLE library against the Expo and React Native baseline, and prove read, write-with-response, notify, reconnect, and retained-result synchronization against real target hardware.
- Open decisions remaining after this spec are the exact microcontroller platform, IR electrical/noise characteristics and qualification rules, selected BLE library after the spike, device identity and production security model, whether STOP is needed for the operator workflow, and when target count should become configurable.
- The implementation should proceed in tracer-bullet slices: establish the protocol and orchestration seam, prove a fake-device session, connect the real BLE adapter and hardware, add persistence and recovery, then harden permissions, accessibility, physical-device coverage, and release packaging.
